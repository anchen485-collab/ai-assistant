# 知识治理维护与上线检查

## 这层功能负责什么

给每个知识片段贴上「是否生效、权威等级、版本、负责人」等标签。
先筛掉失效知识，再在通过相关性门槛的候选中比较治理优先级。
权威等级高不等于内容相关，低相关内容仍应被质量门控拦截。

本模块只负责知识库治理，不提供鉴权或用户权限隔离。
`region`、`product` 当前仅保存与返回，尚未接入用户范围过滤。

## 如何维护配置

配置路径：知识库目录中的 `knowledge_metadata.json`（默认 `src/rag/data/`）。

- `default`：文档共同的默认值；`documents`：按完整文件名覆盖默认值。
- `knowledge_id`：业务可读 ID，每份文档单独设置；内部 `document_id` 仍由同步模块生成。
- 旧配置中的业务 `document_id` 暂时兼容，会转换成 `knowledge_id`，不会覆盖内部 ID。
- 相同正文的不同文档可能有不同治理属性，检索合并时应保留其文档身份。
- 当前配置中的文档仍共享默认权威度和版本；上线前由业务负责人填写真实值，代码不推断权威性。

示例（仅用于说明，数值与日期并非真实业务规则）：

```json
{
  "default": {
    "authority_rank": 0,
    "status": "active"
  },
  "documents": {
    "操作指引.docx": {
      "knowledge_id": "operation-guide",
      "owner": "资料维护团队",
      "authority_rank": 80,
      "version": "1.2",
      "status": "inactive",
      "effective_from": "2026-10-01",
      "effective_to": "2026-12-31"
    }
  }
}
```

| 字段 | 校验与含义 |
| --- | --- |
| `authority_rank` | 非负整数，越大越优先；例如 `80`，不是字符串 `"80"` |
| `version` | 空字符串或数字点分版本；支持 `1.2`、`v1.10`，`1.0` 与 `1.0.0` 等价 |
| `status` | `active` 才参与检索；`inactive`、`archived`、`draft` 均排除 |
| `published_at` | 发布时间；仅保存，不参与排序 |
| `effective_from` / `effective_to` | `YYYY-MM-DD`，空字符串表示该侧不限；起止两天均包含在内 |
| `owner` / `region` / `product` | 字符串，允许留空；地区、产品目前不做过滤 |
| `source_url` | 空字符串或 HTTP/HTTPS 原文链接 |

业务日期固定按北京时间（UTC+8），与部署机器的时区无关。
不支持 `latest`、`1.0-rc1` 等自定义版本顺序；使用已发布的数字版本。

## 配置错误时会发生什么

缺文件、JSON 损坏、重复键、未知字段、错误类型、无效日期、倒置生效区间，
均抛出 `MetadataError`，本次检索停止，不会偷偷采用「全部启用」的默认值。
异常由现有工具层返回检索失败，并保留日志供排查。
读取到缺状态、坏日期或坏排序字段的旧 Chunk，也会将其排除。

因此，不要用删除配置文件来恢复文档，也不要把 `status` 拼成 `stats`。
配置恢复后重新同步；如需启用某文档，显式设为 `active`。
建议在临时文件中编辑并校验，通过后在同目录原子替换正式配置，避免写到一半被读取。

## 修改 metadata 是否重新算向量

本轮保留「该文档重新入库」路线，由增量同步模块负责一致性和故障恢复：
正文或治理标签变化后更新该文档全部 Chunk，而非只改其中一块。
这会重新计算该文档向量，优先保持实现简单和状态一致；不承诺 metadata-only 更新。
正常完成同步后，所有块的业务 ID、状态、版本等应一致。

停用属于逻辑删除：源文档和停用块仍可保留，只是不交给回答链路。
这也不会清除已经发出的回答或旧聊天历史中的文本。

## 测试与上线验收

在 `agent` 项目目录执行（Windows 示例，使用项目已有虚拟环境）：

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_governance*.py" -v
```

- 单元测试：默认覆盖、ID 兼容、错误配置、坏日期、时区、版本比较、状态恢复。
- 集成测试：临时 Chroma + 本地假向量，验证所有 Chunk metadata、停用/恢复、坏配置不改原索引。
- 链路测试：真实调用检索入口，验证记录数不变时停用立即影响下一次查询，恢复后可查，配置损坏则报错。
- 测试不读取真实 Word，不调用付费模型，也不使用正式向量库。

发布前仍需在预发布环境完成：

1. 业务负责人确认文档各自的真实等级、版本、状态、生效日期。
2. 随部署携带配置文件，确认 `KB_SOURCE_DIR` 指向正确目录。
3. 备份原文档、配置、向量库及同步清单，在没有并发写入时做一致性备份。
4. 完成一次同步并测试真实问题：正常文档可检索，停用文档不进入引用，错误配置返回失败。
5. 结合同步模块的锁/恢复方案运行并发检索与更新测试，评估首次迁移成本、延迟和资源占用。
6. 涉及来源文档、检索、同步的版本协同发布；不要单独回退某个公共模块。

本地离线回归通过是发布前证据，不等同于生产环境已经验收或部署。
