# 文档增量同步：可靠性与上线检查

## 本次加固

- 每个 chunk 的 ID 包含文档 ID、内容版本和序号。先写完整新版，再删旧版；解析或向量化准备失败保留旧版，不返回旧库冒充同步成功。
- 同步与检索共用文件锁。调用 `knowledge_read_context()` 包住向量/BM25 两路读取，避免读到切换中的混合版本；模型重排可在锁外执行。
- manifest schema_version=2：记录 scope（目录、集合、模型）、documents（hash 和 chunk 数）、pending（未完成文档）。每篇提交前写 pending，成功后原子替换清单；重启再次同步会核对并恢复。
- JSON 先写同目录临时文件，flush/fsync 后 os.replace；进程中断不会留下截断的正式 JSON。电源故障、磁盘损坏仍依赖备份。
- 文档先复制为快照并核对 Hash，入库提交前再次核对正文和治理配置；变化则报错，下次同步重试。
- 未变化文档跳过 Embedding；同时分页核对已有 chunk ID，库被清空或漏 chunk 时会重建。
- 旧版 manifest 自动迁移；损坏清单、清单丢失但库非空、模型/目录不匹配时停止同步并报错，避免静默误删。
- 批量入库/删除每批 64 条；保留 Small-to-Big 与知识治理 Agent 的全部字段及切分校验。

## 部署前操作

1. 暂停知识库写入与应用请求，备份整个 CHROMA_DIR（数据库、manifest 必须配套）、源文件和治理配置；保存当前代码版本。
2. 每个知识库使用独立 CHROMA_DIR；更换 Embedding 模型时使用新的目录重建，避免不同维度或语义空间混用。
3. 校验知识库目录和 knowledge_metadata.json。空白或损坏文档会报错：修复或移走该文件后重试。
4. 在预发布环境运行上述测试；用生产同款模型执行一次预热入库和实际问答验收。
5. schema/切分版本更新会触发首次重建，产生 Embedding 调用与耗时，安排维护窗口；真实在线模型、容量/延迟压测由预发布验收完成。
6. 确认所有知识库检索入口使用 knowledge_read_context；直接拿旧 store 绕开锁的调用不具备读写一致性保护。

## 恢复和边界

- 普通解析/网络/数据库写入异常：解决原因后重新同步，pending 指明待恢复文档。同步失败应向上游报告，不静默使用过期数据。
- 清单损坏/丢失：停服务，恢复同一时间点的完整数据库+清单快照，或新建 CHROMA_DIR 全量重建；不要只删除 manifest 再试。
- 回滚代码时同步恢复匹配的数据库/清单快照；旧代码不识别 schema=2。检索 Agent 若已依赖新读锁接口，也需协调回滚该调用。
- 建议以单个应用进程部署本地 Chroma。文件锁只解决互斥，未验证多个长期运行 worker 各自缓存的向量索引一致性。
- 此实现面向单机本地持久化目录，采用互斥读写（包含召回读期），不等于分布式事务或高并发架构。网络共享盘/多机部署需另行设计存储与锁。
- 每次同步仍会读取文件计算指纹、扫描 chunk 的 ID/metadata，未承诺大规模知识库的常数时间更新。没有定时任务、后台监听或外部模型自动重试功能。
