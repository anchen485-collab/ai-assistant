# Rerank 质量门控：加固与验收

## 本次范围

只加固已有的精排质量门控，业务实现在 `src/rag/search.py`；不改聊天接口、提示词、模型或默认阈值。
接入其他 Agent 的知识治理/父片段字段，继续保留其召回、入库和 Trace 工作。

流程：召回候选 → 过滤有效文档 → 全候选精排 → 分数达标 → 治理排序 → 取 k 条。
先精排全部候选，是为了不让“相关性略低、但已经达标的权威文档”提前被 top-k 淘汰。

## 每种情况怎么处理

| 情况 | 处理 | Trace decision |
| --- | --- | --- |
| 没有召回候选 | 返回空列表 | blocked_no_candidates |
| 精排成功，但为空/全部条目异常 | 返回空列表，不放行原候选 | blocked_empty_or_invalid_rerank |
| SDK 解析响应失败/未知异常 | 返回空列表，不借故降级 | blocked_empty_or_invalid_rerank |
| 有效分数全低于阈值 | 返回空列表 | blocked_low_rerank_score |
| 有分数大于或等于阈值 | 只放行达标文档，再按治理规则取 k 条 | accepted |
| 未配置 Key、HTTP 永久错误或瞬时故障重试耗尽 | 兼容原行为，返回治理后的 RRF 候选 | rerank_unavailable_use_governed_rrf |

**降级是可用性取舍，不代表质量检查通过。** 降级 Trace 使用 `ok=False`、`quality_gate_applied=False`，并记录实际返回的 selected。
这一策略沿用之前实现；若上线要求所有结果必须通过精排门槛，需要另行决定取消降级。

## 数据校验

- 分数只接受有限的 0～1 数字，拒绝缺失、字符串、布尔值、NaN、无穷和越界数字。
- 索引必须为非布尔整数且落在候选范围内；禁止负索引引用最后一条文档。
- 坏条目丢弃；重复索引只保留第一条有效记录，不采用后来更高的重复分数。
- 使用本地候选正文、来源、父片段标识和治理字段；服务端只提供索引与分数。
- 阈值也必须是有限的 0～1 数字；错误配置直接报错，由已有工具异常分支处理，避免静默放行。

## 超时与重试

- 每次 SDK 请求传入 `request_timeout=10`，已验证会传给 requests 的 timeout，而不是放进模型参数。
- 网络异常、HTTP 408/429/5xx 最多调用 3 次；重试间隔 0.5、1 秒。
- 400/401/403/404 等永久错误不重试；参数、响应格式及未知异常不重试。
- 应用层异常日志只记异常类型，不复制可能带密钥或正文的第三方异常消息。
- requests 的超时不是严格的整个请求墙钟时限；本次没有引入端到端超时调度器或负载限流系统。

在项目目录执行：

```powershell
$env:PYTHONUTF8='1'
& .\.venv\Scripts\python.exe -m unittest discover -s tests -p test_rerank_quality_gate.py -v
```

测试使用真实业务模块、工具和 Trace；替换召回边界与网络，不访问个人知识库或消耗线上模型额度。
另外走真实 DashScope SDK 的请求构造/响应解析流程，在 HTTP 发送边界替换返回值，检查超时参数及损坏响应。

## 上线前仍需验收

本地回归通过不等于线上验收完成。上线前应使用部署环境的 Key/模型/网络，检查正常与无关问题、真实故障降级、耗时和并发负载。
阈值 0.3 保持原值，不是本次通过离线评测得出的最佳阈值。门控只约束检索结果，不证明大模型所有回答均有事实依据。

## 并发合并后的回滚范围

回滚补丁只还原本次 Rerank 调用与门控核心的加固；保留其他 Agent 的混合召回、缓存、读锁、父片段标识、治理接口，以及已共用的入口/阈值参数验证。
脚本默认只做冲突预检，显式传入 `-Apply` 才撤销；发现后续编辑与补丁冲突时整批停止，不覆盖后续工作。
工作区不执行实际回滚；回滚、回滚后的行为对照、冲突保护均在隔离副本验证。
